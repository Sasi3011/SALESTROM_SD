# 05. API & Event Specification

Base URL `https://api.salestorm.example/api/v1`. JSON over HTTPS (TLS 1.2+). Errors use RFC 7807 `application/problem+json`. All write endpoints that could create a business transaction **require** `Idempotency-Key` (UUID v4, generated by the client once per user intent and reused on every retry of that intent).

## 1. Common conventions

| Item | Rule |
|---|---|
| Authentication | `Authorization: Bearer <JWT>` from the identity provider (OIDC). Gateway validates signature, expiry, audience. `customer_id` is taken from the token `sub`, never from the body. |
| Service-to-service | mTLS inside the mesh + short-lived service tokens. |
| Idempotency | `Idempotency-Key` header. Same key + same body → original response replayed with header `Idempotent-Replayed: true`. Same key + different body → `422 IDEMPOTENCY_KEY_REUSED`. Keys kept 24 h. |
| Rate limits | Per user, per IP, and global per endpoint. Exceeded → `429` with `Retry-After` (seconds). |
| Tracing | `traceparent` (W3C) accepted and propagated; `X-Request-Id` returned on every response. |
| Versioning | URI version (`/v1`). Additive changes only within a version. |
| Timeouts (client guidance) | Reserve 2 s, pay 10 s. On timeout, retry with the **same** idempotency key. |

### Error format

```json
{
  "type": "https://api.salestorm.example/errors/sold-out",
  "title": "Sold out",
  "status": 409,
  "code": "SOLD_OUT",
  "detail": "No units of PRODUCT_X are available in sale S1.",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

## 2. Endpoints

### 2.1 Product discovery

| Method | Path | Auth | Description | Responses |
|---|---|---|---|---|
| GET | `/products/{productId}` | none | Product details. CDN-cached 60 s. | 200, 404 |
| GET | `/sales/{saleId}` | none | Sale status and stock badge (`AVAILABLE`, `FEW_LEFT`, `SOLD_OUT`) from Redis. Cached 1 s. | 200, 404 |

### 2.2 Cart

| Method | Path | Auth | Body | Responses |
|---|---|---|---|---|
| POST | `/carts/me/items` | JWT | `{ "productId", "quantity": 1 }` | 201, 400, 409 `LIMIT_EXCEEDED` |
| DELETE | `/carts/me/items/{productId}` | JWT | – | 204 |

Adding to cart does **not** hold stock. Only a reservation holds stock.

### 2.3 Reserve inventory (hot path)

`POST /sales/{saleId}/reservations`

Headers: `Authorization`, `Idempotency-Key` (required)

```json
{ "productId": "PRODUCT_X", "quantity": 1 }
```

| Status | Code | Meaning | Client action |
|---|---|---|---|
| 201 | `RESERVED` | Unit held. Body: `{ reservationId, status, expiresAt }` | Go to payment before `expiresAt` |
| 200 | `RESERVED` (replay) | Duplicate of an earlier successful request | Same as 201 |
| 400 | `VALIDATION_FAILED` | Bad body, quantity ≠ 1 | Fix request |
| 401 | `UNAUTHENTICATED` | Missing/invalid token | Log in |
| 409 | `SOLD_OUT` | No units | Show sold out; optional waitlist |
| 409 | `LIMIT_EXCEEDED` | Customer already holds an active reservation | Show existing reservation |
| 409 | `SALE_NOT_LIVE` | Before start / after end | Show countdown |
| 429 | `RATE_LIMITED` | Throttled | Retry after `Retry-After` with same key |
| 503 | `TEMPORARILY_UNAVAILABLE` | DB failover in progress | Retry with same key |

### 2.4 Reservation

| Method | Path | Auth | Description | Responses |
|---|---|---|---|---|
| GET | `/reservations/{reservationId}` | JWT (owner) | Status, expiry | 200, 404 |
| DELETE | `/reservations/{reservationId}` | JWT (owner) | Customer cancels hold → released | 204, 409 if payment started |

### 2.5 Pay

`POST /checkout/payments`

Headers: `Authorization`, `Idempotency-Key` (required)

```json
{ "reservationId": "rsv_8f2c…", "paymentMethod": "card", "pspToken": "tok_visa_…", "couponCode": null }
```

| Status | Code | Meaning | Client action |
|---|---|---|---|
| 200 | `PAID` | Payment captured; order confirmation follows | Show "Payment received, confirming your order" and poll order |
| 202 | `PAYMENT_PROCESSING` | Gateway timed out; reconciliation running | Poll `GET /payments/{paymentId}`; **do not** pay again |
| 402 | `PAYMENT_FAILED` | Declined | Unit released; offer to try again if stock remains |
| 404 | `NOT_FOUND` | Reservation not found or not owned | – |
| 410 | `RESERVATION_EXPIRED` | Hold timed out before payment started | Start over |
| 503 | `PAYMENT_UNAVAILABLE` | PSP circuit open; hold still valid | Retry after `Retry-After` with same key |

### 2.6 Payment status and webhook

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/payments/{paymentId}` | JWT (owner) | `INITIATED`, `SUCCEEDED`, `FAILED`, `UNKNOWN` |
| POST | `/payments/webhooks/{provider}` | PSP HMAC signature, IP allow-list | PSP result callback. Idempotent on PSP event id. Returns 200 quickly; processing is async. |

### 2.7 Orders and delivery

| Method | Path | Auth | Description | Responses |
|---|---|---|---|---|
| GET | `/orders/{orderId}` | JWT (owner) | Order with status history | 200, 404 |
| GET | `/orders?status=&cursor=` | JWT | My orders, cursor pagination | 200 |
| GET | `/orders/by-reservation/{reservationId}` | JWT (owner) | Lets the client find the order created asynchronously | 200, 404 (not yet) |
| POST | `/orders/{orderId}/cancel` | JWT (owner), `Idempotency-Key` | Allowed before SHIPPED; triggers refund | 202, 409 |
| GET | `/shipments/{shipmentId}/tracking` | JWT (owner) | Courier tracking events | 200 |

### 2.8 Admin

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/admin/sales` | Admin role + MFA | Create sale |
| PUT | `/admin/sales/{saleId}/inventory` | Admin role | Set stock **before** sale start only; seeds Redis gate from DB |
| GET | `/admin/sales/{saleId}/metrics` | Admin role | Live counters |

## 3. Commands vs events

| Kind | Name | Sender → receiver | Transport |
|---|---|---|---|
| Command | `ReserveInventory` | Checkout → Inventory | gRPC (sync) |
| Command | `StartPayment` | Checkout → Inventory | gRPC (sync) |
| Command | `ChargePayment` | Checkout → Payment | gRPC (sync) |
| Command | `RefundPayment` | Order → Payment | Kafka command topic |
| Event | see catalogue | Owner → any subscriber | Kafka via outbox |

**Rule:** a command asks one specific service to do something and can be rejected. An event states a fact that already happened and cannot be rejected, only reacted to.

## 4. Event catalogue

All events carry `eventId` (UUID, used for consumer de-duplication), `occurredAt`, `traceId`, `schemaVersion`. Partition key = `reservationId` so all events of one purchase are ordered.

| Event | Owner (only publisher) | Topic | Key payload | Consumers and their responsibility |
|---|---|---|---|---|
| `ReservationCreated` | Inventory | `inventory.events` | reservationId, customerId, expiresAt | Analytics (conversion funnel) |
| `ReservationExpired` | Inventory | `inventory.events` | reservationId | Notification: "your hold expired"; Order: cancel draft if any |
| `ReservationReleased` | Inventory | `inventory.events` | reservationId, reason | Sale service: refresh stock badge |
| `CheckoutStarted` | Checkout | `checkout.events` | reservationId, customerId, amount | Order: create order CREATED → PAYMENT_PENDING |
| `PaymentSucceeded` | Payment | `payment.events` | paymentId, reservationId, transactionId, amount | Inventory: CONFIRMED (reserved→sold). Order: CONFIRMED |
| `PaymentFailed` | Payment | `payment.events` | paymentId, reservationId, declineCode | Inventory: release unit. Order: CANCELLED. Notification |
| `OrderConfirmed` | Order | `order.events` | orderId, reservationId | Inventory: SOLD. Fulfilment: start. Notification: confirmation |
| `OrderCancelled` | Order | `order.events` | orderId, reason | Payment: refund if captured. Notification |
| `ShipmentCreated` / `ShipmentStatusChanged` | Fulfilment | `shipment.events` | orderId, status, tracking | Order: SHIPPED / OUT_FOR_DELIVERY / DELIVERED. Notification |

### Consumer rules (every consumer)

1. **Idempotent**: check `processed_event (consumer, eventId)` or a state guard before acting.
2. **Commit offset only after** the database transaction commits.
3. **Retry** with exponential backoff (100 ms → 5 s cap) on transient errors; **DLQ** after N attempts; alert on any DLQ message.
4. **Never call back synchronously** into the publisher inside the handler.

  "eventId": "0b8a5f0e-6c1d-4f8e-9a51-3c2a7f8d1e11",

  "occurredAt": "2026-10-05T10:00:01.482Z",

## 5. Try it against the prototype sandbox

With the backend running (`npm start` in `11_AI_Assisted_Validation/prototype/backend`):

```bash
# Reserve (run twice with the same key: second reply has Idempotent-Replayed: true)
curl -i -X POST localhost:4000/api/v1/sales/S1/reservations \
  -H 'Authorization: Bearer demo' -H 'X-Customer-Id: C1' -H 'Idempotency-Key: buy-123' \
  -H 'Content-Type: application/json' -d '{"productId":"PRODUCT_X","quantity":1}'

# Pay (use the reservationId from above)
curl -i -X POST localhost:4000/api/v1/checkout/payments \
  -H 'Authorization: Bearer demo' -H 'X-Customer-Id: C1' -H 'Idempotency-Key: pay-123' \
  -H 'Content-Type: application/json' -d '{"reservationId":"<reservationId from step 1>"}'

curl localhost:4000/api/v1/orders/by-reservation/<reservationId>
curl localhost:4000/api/v1/inventory/PRODUCT_X
curl -X POST localhost:4000/api/v1/sandbox/reset
```

(The sandbox accepts any bearer token and reads the customer from `X-Customer-Id` for demo purposes. Production derives the customer from the JWT.)
