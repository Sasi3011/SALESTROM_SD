# 07. Design Pattern Mapping

| Pattern | Where (prototype file) | Problem it solves in SALESTORM | Trade-off it introduces |
|---|---|---|---|
| **Strategy** | `inventory/strategies/*` (`AtomicConditionalUpdate`, `OptimisticVersioning`, `PessimisticRowLock`, `NaiveReadThenWrite`); proposed `PricingStrategy` | Concurrency control and pricing vary independently from the reservation workflow. Lets us measure alternatives under identical load. | More classes and an indirection; a wrong strategy can be configured (mitigated by defaulting to `atomic`). |
| **Factory** | `StrategyFactory`, `PaymentProviderFactory` | Callers ask for "card" or "atomic" by name from config; they never import concrete classes. | Registry must be kept in sync; runtime error if a name is unknown (fails fast at startup). |
| **State** (table-driven) | `ReservationStateMachine.js`, `OrderStateMachine.js` | Illegal moves (e.g. SOLD → RELEASED, duplicate PaymentSucceeded) are rejected centrally. Prevents corruption from out-of-order or replayed events. | Every new state needs a table update; table form is less expressive than one class per state but far easier to review. |
| **Observer** (publish/subscribe) | `EventBus.subscribe`, consumer groups for inventory, order, fulfilment, notification | Payment does not need to know who cares about `PaymentSucceeded`. New consumers (analytics, loyalty points) plug in without touching Payment. | Eventual consistency; harder to follow a flow (solved with tracing by `traceId`). |
| **Adapter** | `MockPspAdapter` implements `PaymentGateway`; proposed courier adapters | External APIs have their own shapes, errors and auth. The adapter translates them into our interface and error types (`GatewayTimeoutError`). | One more layer to maintain per provider. |
| **Facade** | `CheckoutFacade` | Client calls one endpoint per step; the facade hides Inventory, Payment, idempotency and outbox calls. | Facade must stay thin (no business rules) or it becomes a god object. |
| **Repository** | `InventoryRepository` (each method = one SQL statement) | Persistence details and concurrency-critical SQL are isolated and testable; services speak in domain terms. | Some SQL power (CTEs, bulk ops) hidden behind methods. |
| **Circuit Breaker** | `payment/CircuitBreaker.js` around every PSP call | A failing PSP would otherwise tie up threads/sockets with 3 s timeouts and cascade into checkout. Breaker fails fast and probes recovery (HALF_OPEN). | Some customers are told "try again" while the PSP might already have recovered; thresholds need tuning. Declines do not trip it. |
| **Transactional Outbox** | `core/Outbox.js` | Removes the dual-write problem: state change and event are committed together. | Extra table + relay; events are delayed by the relay interval (40 ms in prototype). |
| **Idempotent Receiver / Idempotency Key** | `IdempotencyStore`, `PaymentService` unique key, consumer state guards | Retries, double-clicks and redelivered events become harmless. | Storage for keys (24 h TTL), extra lookup per request. |
| **Saga (choreography) with compensation** | Events Checkout → Payment → Inventory/Order; refund on `OrderCancelled` | Multi-service purchase without distributed transactions. | Intermediate states visible (e.g. PAID but order PAYMENT_PENDING for a few seconds). |
| **Token Bucket / Rate Limiter** | `gateway/RateLimiter.js` | Back-pressure at the edge; protects core services during the burst. | Legitimate users can get 429 at peak (they retry with Retry-After). |
| **Composition Root / Dependency Injection** | `simulation/System.js` | One place wires concrete classes; enables DIP and test doubles. | Wiring code grows with the system. |
